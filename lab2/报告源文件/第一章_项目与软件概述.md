# 一、项目与软件概述

## 1. 选择的项目

本实验延续实验一的项目：题目 5——活动票务与报名系统。实验一完成了该系统的需求分析，产出 24 条需求（功能需求 18 条、非功能需求 6 条）与配套的访谈记录、验收标准（仓库 lab1-ai-draft / lab1-final 两个标签）。本实验在此需求基线上完成软件设计与建模，产出模块划分、六张 UML 图与十屏 UI 界面。

## 2. 软件的主要功能

系统面向四类角色：参与者（观众）、组织者、检票人员、平台管理员。主要功能如下：

| 功能域 | 说明 | 主要需求 |
|---|---|---|
| 账号与权限 | 手机号注册登录、实名认证、角色权限、忘记密码自助重置、账号封禁 | REQ-001/017/019 |
| 演出发布与审核 | 组织者提交演出申请（含场次与票档），管理员审核（驳回须给原因，可修改再报，不限次数），按约定时间上线 | REQ-002/003/004 |
| 查询与展示 | 按时间、地点、主讲/明星、主题筛选在售演出，查看场次余票（可购/可候补）与购票退票规则公示 | REQ-005 |
| 购票与支付 | 实名购票（每账号每场次限购 1 张），3 分钟站内模拟支付，出票时后台按票档统一分配座位并生成唯一票码 | REQ-006/007 |
| 候补与退款 | 票档售罄转候补，预付全款排队，递补自动出票，截止未递补全额原路退回；阶梯退票（>7 天收 20%、3–7 天收 40%、不足 3 天不可退） | REQ-008/009/021 |
| 演出变更 | 改期/改址须重新审核，通过后站内通知全部已购票用户，用户可选按原价全额退款 | REQ-010 |
| 检票入场 | 管理员开启签到窗口（演出前约 3 小时），检票员输入票码并核对身份证核销放行；演出结束未检票转缺席 | REQ-011/012 |
| 统计与导出 | 按场次统计上座率、购票总人数、实际到场、候补、退票；组织者导出观众名单（姓名、联系方式、座位号） | REQ-014/015 |
| 全程审计 | 关键操作（审核、支付、退票、核销、封禁、导出等）记录操作者/时间/动作/对象/前后值，不可删改 | REQ-016 |

## 3. 明确不实现的内容

不接入真实支付与短信（站内模拟支付、站内消息）；不做二维码与人脸识别（入场凭证为唯一票码字符串）；不做座位图选座（后台按票档统一分配）；不做公益免费票与票转让（REQ-013 已拒绝）；不做黄牛自动检测（实名限购 + 管理员手动封禁替代）。

## 4. 数据与状态约束

设计与后续实现共同遵守以下约束（详见类图与状态图）：

- 订单状态机共 9 个状态：待支付、候补中、已出票、已签到、已核销、已缺席、已取消、已关闭、已退款；其中 5 个终态不可再转换。
- 可售余票 = 票档总量 − 有效订单数（待支付与已出票），随支付、关闭、退票、递补实时同步；票档售罄自动转候补。
- 退款金额 = 实付金额 − 应扣手续费，原路退回。
- 唯一性约束：手机号、身份证号、票码全平台唯一；同一账号同一场次仅一条有效订单。
