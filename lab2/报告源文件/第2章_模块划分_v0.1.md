## 1. 划分原则

**原则一：按业务生命周期切，不按技术层切。**
活动从"申请 → 审核 → 上线 → 售票 → 检票 → 统计"是一条链，每个环节的责任人不同（组织者、管理员、参与者、检票人员）。按这条链切模块，模块边界与权限边界自然重合，后续做权限控制和用例图都不会打架。

**原则二：一个共享数据只留一个写入口。**
全系统最敏感的数据是「票档余票」。余票的写入口收敛在交易模块（售票·候补·退款）内部——候补与退款并入后，超售防护从跨模块约束变成模块内实现。

**原则三：横切关注点收敛到支撑模块。**
审计日志、站内通知、故障回退被几乎所有模块使用。若每个业务模块各写一套，日志格式、通知渠道会各说各话。因此统一收敛到平台支撑模块。

**原则四：职责单一到"只有一个变更理由"。**
统计规则变了只动统计模块；审核流程变了只动活动模块；票务规则变了才动交易模块。

## 2. 模块清单

| 编号 | 模块 | 一句话职责 | 覆盖需求 |
|---|---|---|---|
| M1 | 账号与权限模块 | 注册登录、实名认证、四类角色权限、封禁 | REQ-001、017、019、024 |
| M2 | 活动发布与审核模块 | 活动/场次/票档的提交、审核、上线、改期取消 | REQ-002、003、004、010 |
| M3 | 查询展示模块 | 多条件查询、余票状态、规则公示 | REQ-005 |
| M4 | 交易模块（售票·候补·退款） | 限购校验、下单、模拟支付、出票、余票扣减、候补队列、自动递补、阶梯退票、退款执行 | REQ-006、007、008、009、020、021、023 |
| M5 | 检票模块 | 签到窗口、票码核销、缺席判定 | REQ-011、012 |
| M6 | 统计与导出模块 | 场次统计、名单导出 | REQ-014、015 |
| M7 | 平台支撑模块 | 审计日志、站内通知、一致性保障 | REQ-016、022 |

### M1 账号与权限模块
- **负责**：手机号+密码注册/登录/重置；实名认证（姓名+身份证号，双向唯一）；四类角色的权限判定；管理员封禁与解封。
- **不负责**：不判断"这个用户能不能买这一场"（那是交易模块的限购规则），也不管可见字段过滤（那是各查询模块按角色取数）。
- **对外能力**：登录校验、当前用户身份与角色、实名信息读取、封禁状态检查。
- **依赖**：平台支撑（封禁操作留痕）。

### M2 活动发布与审核模块
- **负责**：活动与场次、票档的创建与提交；管理员审核（通过/驳回+必填原因，不设次数上限）；按约定时间上线；改期/改址/取消的申请与审核；活动主线状态流转（待审核→上线→在售中→已截止→检票中→已结束/已取消）。
- **不负责**：不卖票、不算余票（交易模块），不负责通知投递（平台支撑）。
- **对外能力**：可售场次与票档查询、报名截止时间、签到窗口控制。
- **依赖**：平台支撑（改期/取消后的站内通知、审计日志）。

### M3 查询展示模块
- **负责**：按时间、地点、主演或主讲、主题多条件筛选在售活动；展示各场次余票状态（可购/可候补/已售罄）与购票退票规则；组织者查看自己活动的售票情况与审核进度；管理员按活动编号/订单号/用户 ID 查询。
- **不负责**：不计算结果性数据，余票与统计一律向交易、平台支撑取。
- **依赖**：活动发布与审核（活动数据）、交易（余票实时数）。

### M4 交易模块（售票·候补·退款）
- **负责**：限购校验（每账号每场次限 1 张）；创建订单并进入待支付；3 分钟模拟支付与超时关闭；出票（按票档统一分配座位、生成唯一票码）；**余票扣减与回池的唯一写入口**；订单状态机（9 状态、9 条允许转换）；票档售罄后的候补申请与预付、按先来后到维护唯一队列、自动递补首位出票、阶梯退票手续费计算（>7 天 20%、3–7 天 40%、不足 3 天禁止）与退款执行。
- **不负责**：不核销（检票模块），不生成统计报表（统计与导出模块）。
- **对外能力**：下单、查余票、关闭订单、候补入队与递补、退款执行。
- **依赖**：账号与权限（实名与限购所需身份）、平台支撑（审计日志）。


### M5 检票模块
- **负责**：签到窗口开启（演出前约 3 小时）；输入票码+核对身份证号核销；重复核验、已取消、伪造票码、窗口未开四种异常分别提示；演出结束后未检票订单转已缺席。
- **不负责**：不提供任何查询功能（REQ-005 明确检票人员无查询权限）。
- **依赖**：交易（订单与票码）、活动发布与审核（场次与签到窗口）、平台支撑（审计日志）。

### M6 统计与导出模块
- **负责**：按场次统计出票数、到场人数、候补人数、退票数、上座率；按活动/场次导出名单（姓名、联系方式、座位号，**不含身份证号**）；导出行为留审计。
- **不负责**：不持有业务数据，只聚合交易与检票的记录。
- **依赖**：交易、检票（数据源）、平台支撑（导出审计）。

### M7 平台支撑模块
- **负责**：审计日志（操作者、时间、动作、对象、状态前后值；不可删改、可按对象查询）；站内通知（改期/取消、候补递补、退款结果）；一致性保障（故障恢复后"要么完成要么回退"，不留半完成订单）。
- **不负责**：不承载业务规则。
- **被依赖**：全部业务模块（M1～M6）。
- **说明**：站内通知与模拟支付都是**系统内部能力**——通知由平台支撑承载；模拟支付并入交易模块（REQ-007，本项目不接入真实支付），不引入外部系统。

## 3. 模块间交互

### 3.1 主流程的调用链

| 业务流程 | 调用链 |
|---|---|
| 活动上线 | 组织者 → 活动发布与审核受理 → 请求平台支撑记审核 → 上线 → 平台支撑发通知 |
| 购票 | 查询展示查询 → 交易限购校验 → 扣减余票 → 创建订单 → 待支付 → 支付成功 → 交易出票 → 平台支撑记日志 |
| 售罄转候补 | 交易返回"售罄" → 交易模块内转候补（预付）→ 入队 |
| 退票递补 | 交易模块内算手续费 → 释放名额回池 → 队列非空则递补队首出票，否则仅回池（同模块内完成） |
| 检票 | 检票校验窗口 → 核验票码+身份证 → 交易把订单转已签到 → 平台支撑记日志 |
| 统计导出 | 统计与导出聚合交易与检票记录 → 生成报表/名单 → 平台支撑记导出审计 |
| 活动取消 | 活动发布与审核通过 → 交易全额退款 → 平台支撑通知全部购票用户 |

### 3.2 共享数据的归属与同步

| 数据 | 唯一所有者 | 谁可以读 | 谁可以写 |
|---|---|---|---|
| 票档余票（已售数） | 交易 | 查询展示、统计与导出 | **仅交易** |
| 订单与票码 | 交易 | 检票、统计与导出 | 交易（状态转换）；检票只能触发"已签到" |
| 候补队列 | 交易 | 统计与导出 | 仅交易 |
| 审计日志 | 平台支撑 | 管理员 | 各模块通过平台支撑追加，无人可改 |
| 活动/场次/票档定义 | 活动发布与审核 | 查询展示、交易、检票、统计与导出 | 仅活动发布与审核（上线后容量与价格冻结） |

**同步规则**：任一票档可售余票 = 总量 − 有效订单数（待支付 + 已出票）。支付、超时关闭、退票、递补四种事件发生后，都由交易模块在同一个事务里更新余票并写日志（REQ-020、REQ-022）。

### 3.3 依赖方向

```
平台支撑（无业务依赖，被所有人依赖）
账号与权限 ← 查询展示、交易、检票、统计与导出
活动发布与审核 ← 查询展示、交易、统计与导出
交易 ← 查询展示、统计与导出
统计与导出 ← 交易、检票
```

设计上要求**依赖不成环**。候补与退款并入交易模块后，原售票与候补退款两模块之间的方向问题消失；检票、统计对交易的依赖保持单向。模块内部的售票与候补退款两层，实现时仍要保持单向调用。

### 4.2 非功能需求（6 条）——横切，不单独成模块

非功能需求没有"行为"，强行做成模块会得到一个空壳。正确做法是给每条指出**落在哪些模块的哪个环节**，并说明设计上靠什么保证。

| 编号 | 需求名称 | 落点 | 设计上如何保证 |
|---|---|---|---|
| REQ-018 | 查询响应性能 | 查询展示、交易 | 查询走只读路径（查询展示不写业务数据）；余票由订单推导，不维护冗余计数 |
| REQ-019 | 密码存储安全 | 账号与权限 | 只存密码哈希；任何接口不返回密码字段 |
| REQ-020 | 购票数据一致性（不超售、队列有序） | 交易（含候补与退款） | 余票唯一写入口在交易模块内；候补记录以排队序号排序 |
| REQ-021 | 退款金额一致性 | 交易 | 退款与手续费在同一个服务方法内计算并落库 |
| REQ-022 | 故障回退与可靠性 | 平台支撑（横切全部写操作） | 扣名额、建订单、写日志放在同一事务；失败整体回退 |
| REQ-024 | 角色数据可见范围 | 账号与权限 + 查询展示/统计与导出取数 | 角色判定集中在账号与权限；查询模块按角色裁剪返回字段 |

### 4.4 覆盖检查结论

1. **24 条全部有落点**：功能需求 17 条 + 已拒绝 1 条（明确不实现）+ 非功能需求 6 条（标注横切落点）。

## 5. 明确不在范围内的

1. 票转让（REQ-013，甲方已拒绝）；
2. 真实支付与真实短信：支付为站内模拟，通知只走站内消息；
3. 人脸识别与二维码：入场凭证为唯一票码字符串；
4. 座位图选座：座位由交易模块按票档统一分配；
5. 黄牛自动检测：以实名限购 + 管理员手动封禁替代。

## 6. 审核清单（人工修改时逐条核对）

1. **逐条对表**：翻 requirements.md 的 24 条，每条是否都能在上面的对齐表里找到归属？找不到的先记下来，别猜。
2. **余票写入口是否唯一**：候补与退款已并入交易模块，退票与递补不再跨模块调用；实现时仍要保证余票扣减收敛在同一处代码。
3. **模块依赖是否成环**：合并后原售票与候补退款的方向问题消失；检票、统计对交易的依赖保持单向。
4. **系统内组件的归位**：站内通知归平台支撑，模拟支付并入交易模块，二者都是系统内部能力、不标外部系统。这一条要和组件图保持一致。
5. **模块与界面是否对得上**：7 个业务模块对 10 屏 UI，平台支撑没有独立界面——合理吗？如果不合理，是加一屏"审计日志查询"还是并进管理员界面？
6. **拒绝的需求有没有混进来**：全文搜一遍"转让""选座""二维码""检测"，不该出现的删掉。
7. **命名是否统一**：模块名 = 组件图的组件名 = 类图的包名？定稿后后面的图直接照抄，不要再起别名。

## 7. 这一章在报告里怎么写

- 第 1 节（原则）压成 4 条要点，每条配一句"如果不这样会怎样"；
- 第 2 节用模块表 + 每个模块 2～3 句职责说明（"负责什么/不负责什么"比只写"负责什么"更能体现设计思考）；
