## 1. 划分原则

**原则一：按业务生命周期切，不按技术层切。**
活动从"申请 → 审核 → 上线 → 售票 → 检票 → 统计"是一条链，每个环节的责任人不同（组织者、管理员、参与者、检票人员）。按这条链切模块，模块边界与权限边界自然重合，后续做权限控制和用例图都不会打架。

**原则二：一个共享数据只留一个写入口。**
全系统最敏感的数据是「票档余票」。若售票模块和候补退款模块都能改已售数，就必然出现超售（违反 REQ-020）。因此余票的写入口只保留在售票模块，候补退款模块退票后只能"申请释放名额"，由售票模块实际回池。

**原则三：横切关注点收敛到支撑模块。**
审计日志、站内通知、故障回退被几乎所有模块使用。若每个业务模块各写一套，日志格式、通知渠道会各说各话。因此统一收敛到平台支撑模块。

**原则四：职责单一到"只有一个变更理由"。**
统计规则变了只动统计模块；审核流程变了只动活动模块；票务规则变了才动售票模块。

## 2. 模块清单

| 编号 | 模块 | 一句话职责 | 覆盖需求 |
|---|---|---|---|
| M1 | 账号与权限模块 | 注册登录、实名认证、四类角色权限、封禁 | REQ-001、017、019、024 |
| M2 | 活动发布与审核模块 | 活动/场次/票档的提交、审核、上线、改期取消 | REQ-002、003、004、010 |
| M3 | 查询展示模块 | 多条件查询、余票状态、规则公示 | REQ-005 |
| M4 | 售票模块 | 限购校验、下单、模拟支付、出票、余票扣减 | REQ-006、007、020、023 |
| M5 | 候补与退款模块 | 候补队列、自动递补、阶梯退票、退款执行 | REQ-008、009、021 |
| M6 | 检票模块 | 签到窗口、票码核销、缺席判定 | REQ-011、012 |
| M7 | 统计与导出模块 | 场次统计、名单导出 | REQ-014、015 |
| M8 | 平台支撑模块 | 审计日志、站内通知、一致性保障 | REQ-016、022 |

### M1 账号与权限模块
- **负责**：手机号+密码注册/登录/重置；实名认证（姓名+身份证号，双向唯一）；四类角色的权限判定；管理员封禁与解封。
- **不负责**：不判断"这个用户能不能买这一场"（那是 M4 的限购规则），也不管可见字段过滤（那是各查询模块按角色取数）。
- **对外能力**：登录校验、当前用户身份与角色、实名信息读取、封禁状态检查。
- **依赖**：M8（封禁操作留痕）。

### M2 活动发布与审核模块
- **负责**：活动与场次、票档的创建与提交；管理员审核（通过/驳回+必填原因，不设次数上限）；按约定时间上线；改期/改址/取消的申请与审核；活动主线状态流转（待审核→上线→在售中→已截止→检票中→已结束/已取消）。
- **不负责**：不卖票、不算余票（M4），不负责通知投递（M8）。
- **对外能力**：可售场次与票档查询、报名截止时间、签到窗口控制。
- **依赖**：M8（改期/取消后的站内通知、审计日志）。

### M3 查询展示模块
- **负责**：按时间、地点、主演或主讲、主题多条件筛选在售活动；展示各场次余票状态（可购/可候补/已售罄）与购票退票规则；组织者查看自己活动的售票情况与审核进度；管理员按活动编号/订单号/用户 ID 查询。
- **不负责**：不计算结果性数据，余票与统计一律向 M4、M7 取。
- **依赖**：M2（活动数据）、M4（余票实时数）。

### M4 售票模块
- **负责**：限购校验（每账号每场次限 1 张）；创建订单并进入待支付；3 分钟模拟支付与超时关闭；出票（按票档统一分配座位、生成唯一票码）；**余票扣减与回池的唯一写入口**；订单状态机（9 状态、9 条允许转换）。
- **不负责**：不维护候补队列（M5），不核销（M6）。
- **对外能力**：下单、支付、查余票、关闭订单、释放名额（供 M5 退票调用）。
- **依赖**：M1（实名与限购所需身份）、M8（审计日志）。

### M5 候补与退款模块
- **负责**：票档售罄后的候补申请与预付；按先来后到维护唯一队列；出现名额时自动递补首位并出票；阶梯退票手续费计算（>7 天 20%、3–7 天 40%、不足 3 天禁止）；退款金额与"实付−手续费"严格一致；候补失败全额退款。
- **不负责**：不直接改票档已售数（必须调 M4 的释放名额接口），不直接改订单状态为已出票（由 M4 出票）。
- **依赖**：M4（释放名额、出票）、M8（退款通知、审计日志）。

### M6 检票模块
- **负责**：签到窗口开启（演出前约 3 小时）；输入票码+核对身份证号核销；重复核验、已取消、伪造票码、窗口未开四种异常分别提示；演出结束后未检票订单转已缺席。
- **不负责**：不提供任何查询功能（REQ-005 明确检票人员无查询权限）。
- **依赖**：M4（订单与票码）、M2（场次与签到窗口）、M8（审计日志）。

### M7 统计与导出模块
- **负责**：按场次统计出票数、到场人数、候补人数、退票数、上座率；按活动/场次导出名单（姓名、联系方式、座位号，**不含身份证号**）；导出行为留审计。
- **不负责**：不持有业务数据，只聚合 M4/M5/M6 的记录。
- **依赖**：M4、M5、M6（数据源）、M8（导出审计）。

### M8 平台支撑模块
- **负责**：审计日志（操作者、时间、动作、对象、状态前后值；不可删改、可按对象查询）；站内通知（改期/取消、候补递补、退款结果）；一致性保障（故障恢复后"要么完成要么回退"，不留半完成订单）。
- **不负责**：不承载业务规则。
- **被依赖**：M1～M7。
- **说明**：站内通知与模拟支付都是**系统内部能力**——通知由 M8 承载；模拟支付是独立的站内模拟组件（REQ-007，本项目不接入真实支付），不属于 M1～M8 的业务模块编号。

## 3. 模块间交互

### 3.1 主流程的调用链

| 业务流程 | 调用链 |
|---|---|
| 活动上线 | 组织者 → M2 提交 → M2 请求 M8 记审核 → M2 上线 → M8 通知 |
| 购票 | M3 查询 → M4 限购校验 → M4 扣减余票 → M4 创建订单 → 待支付 → 支付成功 → M4 出票 → M8 记日志 |
| 售罄转候补 | M4 返回"售罄" → 调用方转 M5 提交候补（预付）→ M5 入队 |
| 退票递补 | M5 算手续费 → M5 调 M4 释放名额 → M4 回池 → M4 通知 M5 递补 → M5 取队首 → M4 出票 |
| 检票 | M6 校验窗口 → M6 核验票码+身份证 → M4 订单转已签到 → M8 记日志 |
| 统计导出 | M7 聚合 M4/M5/M6 → 生成报表/名单 → M8 记导出审计 |
| 活动取消 | M2 审核通过 → M5 全额退款 → M8 通知全部购票用户 |

### 3.2 共享数据的归属与同步

| 数据 | 唯一所有者 | 谁可以读 | 谁可以写 |
|---|---|---|---|
| 票档余票（已售数） | M4 | M3、M5、M7 | **仅 M4** |
| 订单与票码 | M4 | M5、M6、M7 | M4（状态转换）；M6 只能触发"已签到" |
| 候补队列 | M5 | M7 | 仅 M5 |
| 审计日志 | M8 | 管理员 | 各模块通过 M8 追加，无人可改 |
| 活动/场次/票档定义 | M2 | M3、M4、M6、M7 | 仅 M2（上线后容量与价格冻结） |

**同步规则**：任一票档可售余票 = 总量 − 有效订单数（待支付 + 已出票）。支付、超时关闭、退票、递补四种事件发生后，都由 M4 在同一个事务里更新余票并写日志（REQ-020、REQ-022）。

### 3.3 依赖方向

```
M8（无业务依赖，被所有人依赖）
M1 ← M4, M6, M3, M7
M2 ← M3, M4, M6
M4 ← M3, M5, M6, M7
M5 ← M7
M6 ← M7
```

设计上要求**依赖不成环**：M4 不反向依赖 M5。售罄时 M4 只返回"售罄"结果，由购票流程（上层）去调 M5，这样 M4 与 M5 之间保持单向。这是本设计里唯一需要小心处理的耦合点。

### 4.2 非功能需求（6 条）——横切，不单独成模块

非功能需求没有"行为"，强行做成模块会得到一个空壳。正确做法是给每条指出**落在哪些模块的哪个环节**，并说明设计上靠什么保证。

| 编号 | 需求名称 | 落点 | 设计上如何保证 |
|---|---|---|---|
| REQ-018 | 查询响应性能 | M3、M4 | 查询走只读路径（M3 不写业务数据）；余票由订单推导，不维护冗余计数 |
| REQ-019 | 密码存储安全 | M1 | 只存密码哈希；任何接口不返回密码字段 |
| REQ-020 | 购票数据一致性（不超售、队列有序） | M4（M5 配合） | 余票唯一写入口在 M4；候补记录以排队序号排序 |
| REQ-021 | 退款金额一致性 | M5 | 退款与手续费在同一个服务方法内计算并落库 |
| REQ-022 | 故障回退与可靠性 | M8（横切全部写操作） | 扣名额、建订单、写日志放在同一事务；失败整体回退 |
| REQ-024 | 角色数据可见范围 | M1 + M3/M7 取数 | 角色判定集中在 M1；查询模块按角色裁剪返回字段 |

### 4.4 覆盖检查结论

1. **24 条全部有落点**：功能需求 17 条 + 已拒绝 1 条（明确不实现）+ 非功能需求 6 条（标注横切落点）。
2. **主责唯一**：每条需求只由一个模块承担主责，其余模块只在表里标"配合"，避免同一规则两处实现。
3. **没有空模块**：M1～M8 每个至少有一条主责需求；若将来某个模块的需求被删空，应考虑合并该模块。
4. **REQ-013 与需求文档一致**：状态为"已拒绝"，在设计里不出现任何对应类、用例或界面。

## 5. 明确不在范围内的

1. 票转让（REQ-013，甲方已拒绝）；
2. 真实支付与真实短信：支付为站内模拟，通知只走站内消息；
3. 人脸识别与二维码：入场凭证为唯一票码字符串；
4. 座位图选座：座位由 M4 按票档统一分配；
5. 黄牛自动检测：以实名限购 + 管理员手动封禁替代。

## 7. 这一章在报告里怎么写

- 第 1 节（原则）压成 4 条要点，每条配一句"如果不这样会怎样"；
- 第 2 节用模块表 + 每个模块 2～3 句职责说明（"负责什么/不负责什么"比只写"负责什么"更能体现设计思考）；
- 第 3 节是全章最能拿分的部分：**讲清"余票只有一个写入口"和"依赖不成环"这两个决定，以及为什么**；
- 第 4 节的对齐表可以整张放进报告，证明设计覆盖了需求；
- 第 5、6 节不要原样搬进报告，第 6 节是你审核时用的工作清单。
