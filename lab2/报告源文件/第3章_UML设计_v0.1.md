## 3.1 类图

图展示核心领域模型：14 个类（含 2 个 «同一类» 副本）。模块归属用底色区分——蓝 = M1 账号与权限，绿 = M2 活动发布与审核，橙 = M4+M5 交易，紫 = M6+M7 现场与运营，灰 = M8 平台支撑。不画包框而用配色，是为了让布局引擎自由排布、做到连线零交叉；模块与类的完整对应见第 2 章 4.3 节的反查表。

此外有四处呈现技巧：① 布局按"从上到下读"设计——右上角是账号体系（四个角色泛化箭头向上指向用户，教科书惯例），中轴是业务主链（组织者提交 → 活动 → 场次 → 票档 → 订单 → 审计日志，垂直向下），左侧一列是与主链各环节一一对应的记录（检票记录对应场次核销、候补记录对应票档排队），退款作为订单的关联放在主链右侧收尾，读图顺序即业务顺序；② 参与者与组织者各有一个带构造型 «同一类» 的副本，就近画在订单与活动旁边——UML 允许同一元素在图中出现多次，副本只承担业务关联（购买、提交），继承关系由右侧的角色原块表达，两条线因此从横贯全图变成局部短线；③ 审计日志与业务对象之间只画出"订单 → 审计日志"一条依赖线作为代表，活动、检票等对象的写入不再重复，图旁注释已说明；④ 布局方向逐条手工指定（-up-/-down-/-left-/-right-），保证连线零交叉。

**取舍原则**：能说明"业务对象是什么、谁归谁"的保留；派生数据、横切记录、架构层对象一律不进类图。被移出的对象及去向见本节末尾。

1. **参与者 / 组织者 / 检票人员 / 平台管理员 —— 泛化自 用户**
   - 逻辑关系：四类角色共享账号、实名与状态，只在"能做什么"上不同。
   - 设计原因：登录、实名、状态若各写一遍要重复四份；泛化后权限判定集中在一处（REQ-001、REQ-024）。

2. **用户（含角色、实名、封禁状态字段）**
   - 逻辑关系：角色用枚举取值表达（参与者/组织者/检票人员/管理员），与四个角色子类互为呼应；姓名、身份证号承载实名。
   - 设计原因：实名与封禁都是"账号的属性"而非独立业务对象；封禁的多次操作记录由审计日志承担（REQ-001、REQ-017）。

3. **组织者 1 —— \* 活动**
   - 逻辑关系：活动必须属于一个组织者，一个组织者可办多个活动。
   - 设计原因：审核驳回后的修改、下线后的追责都依赖这条归属（REQ-002、REQ-003）。

4. **活动 1 ◆—— 1..\* 场次（组合）**
   - 逻辑关系：场次脱离活动没有意义，活动取消后场次一并失效。
   - 设计原因：生命周期一致；若用聚合，就要额外处理"活动已删、场次还在"的脏数据（REQ-004）。

5. **场次 1 ◆—— 1..\* 票档（组合）**
   - 逻辑关系：票档是场次内的价格分区，场次删除后票档不存在。
   - 设计原因：座位分配、余票扣减、统计都以票档为最小单位（REQ-004、REQ-015）。

6. **活动 1 —— \* 审核记录**
   - 逻辑关系：一个活动可能经历多轮审核（驳回→修改→再申请，次数不限）。
   - 设计原因：只保留最新结论会丢失历史，而驳回原因是组织者修改的依据（REQ-003）。

7. **参与者 1 —— \* 订单**
   - 逻辑关系：一个人可买多个不同场次的票；同一场次限购 1 张。
   - 设计原因：限购是业务规则（由售票过程校验），不是数据结构限制，所以关系用一对多（REQ-006）。

8. **票档 1 —— \* 订单**
   - 逻辑关系：订单从某个票档售出；可售余票 = 总量 − 有效订单数。
   - 设计原因：余票不单独存字段，而是由订单推导，避免"余票与实际订单不一致"（REQ-020）。

9. **订单 1 —— 0..1 退款**
   - 逻辑关系：只有退票、活动取消、候补失败等情况才有退款，一单最多一笔。
   - 设计原因：用 0..1 表达"不是每单都退"；退款金额与手续费必须可核对（REQ-009、REQ-021）。

10. **订单.状态 字段**
    - 逻辑关系：订单状态有 9 种取值，类图中以字段表示，完整的状态机单独画在状态图里。
    - 设计原因：状态机是独立的一张图（REQ-023），类图里再画一个 9 行的枚举框只会增加高度，不增加信息。

11. **票档 1 —— \* 候补记录**
    - 逻辑关系：同一票档只有一条候补队列，记录按排队序号排序。
    - 设计原因：队列顺序是硬要求，序号必须显式存储（REQ-008、REQ-020）。

12. **候补记录 ..> 订单（依赖）**
    - 逻辑关系：递补成功时才生成订单。
    - 设计原因：候补记录先存在、订单后产生，两者不同时创建，用依赖而非组合（REQ-008）。

13. **场次 1 —— \* 检票记录；订单 1 —— 0..1 检票记录**
    - 逻辑关系：一次核销关联"哪个场次、哪张票"；检票员以属性记录。
    - 设计原因：按场次查到场人数、按票识别重复核验；订单端 0..1 保证重复核验能被识别（REQ-011、REQ-012）。

14. **审计日志独立存在**
    - 逻辑关系：只记对象类型 + 对象ID + 状态前后值，不与业务类建立关联。
    - 设计原因：给每个类都连一条线会变成蜘蛛网；用 ID 引用实现同样的可追溯性（REQ-016）。

## 3.2 组件图

图展示 8 个业务模块、1 个站内模拟支付组件、2 个对外接口和若干依赖关系，四类角色用户位于系统框外顶部。布局按调用方向分四层：顶部是四类角色用户；其下一行是对外接口与发起调用的模块（查询展示、账号与权限、统计与导出、检票、候补与退款）；再下是被依赖的售票(M4)与活动发布与审核(M2)——M4 被 4 个模块依赖，是全局枢纽，故置于图的中心；底部是平台支撑(M8)与模拟支付。接口符号只留给被多方复用的能力：登录面向全部四类角色、下单被候补与退款(M5)递补复用，二者画在系统框内、紧贴所属模块；核销仅检票人员一人使用，由角色直达检票(M6)，不设接口符号，角色出发的三条线因此呈扇形展开、互不交叉。模拟支付是系统内的模拟支付网关组件——REQ-007 确认本项目不接入真实支付，独立成组件以便日后替换真实支付，故不标注为外部系统。依赖方向自上而下，全程无交叉；实现上用少量隐藏锚点边固定行列顺序（仅定位、不表达关系）。每个模块框内以小字标注该模块的代表性职责，与第 2 章模块划分对应。

1. **账号与权限(M1) — 登录接口**
   - 逻辑关系：所有角色登录都经过 M1，M1 对外暴露"登录"。
   - 设计原因：把鉴权收敛到一个组件，其他模块不再各自校验密码（REQ-001、REQ-019）。

2. **售票(M4) — 下单接口；候补与退款(M5) 使用同一下单接口**
   - 逻辑关系：下单是 M4 提供的唯一写入口，M5 递补出票时复用。
   - 设计原因：同一个入口才能保证限购与余票校验不被绕过（REQ-006、REQ-020）。

3. **检票人员 → 检票(M6)：核销票码**
   - 逻辑关系：检票人员是核销的唯一使用者，直达模块。
   - 设计原因：核销涉及座位、票码、签到窗口，收在 M6 内独占校验逻辑（REQ-011）；接口符号只留给被复用的能力（登录、下单），核销单一入口，直连更直观。

4. **查询展示(M3) ..> 售票(M4)：查询余票；查询展示(M3) ..> 活动发布与审核(M2)：查询活动**
   - 逻辑关系：M3 只读，不写任何业务数据。
   - 设计原因：读写分离，查询压力不落到写入口上（REQ-005、REQ-018）。

5. **候补与退款(M5) ..> 售票(M4)：释放名额**
   - 逻辑关系：M5 退票后请求 M4 回池，自己不直接改已售数。
   - 设计原因：这是"余票唯一写入口"的落地方式，也是避免超售的关键（REQ-020）。

6. **售票(M4) ..> 模拟支付：发起模拟支付**
   - 逻辑关系：M4 调用站内模拟支付完成收款，支付结果回写订单。
   - 设计原因：REQ-007 确认不接入真实支付、只做站内模拟；独立成组件并只依赖其接口，模拟收单与原路退回（REQ-021）都在该组件内，日后替换真实支付只改这一处。

7. **售票(M4) ..> 平台支撑(M8)：写审计日志；活动发布与审核(M2) ..> 平台支撑(M8)：发送站内通知**
   - 逻辑关系：所有模块的关键操作都写入 M8，图中只画两条代表线。
   - 设计原因：横切能力集中，避免每个模块各写一套日志与通知（REQ-016、REQ-010）。

## 3.3 用例图

图展示 4 类角色、16 个用例、3 个 include 与 1 个 extend。未画系统边界框：图题已表明系统范围，且用例按角色分组排列，边界自明。布局分四层：左上组织者、右上平台管理员（两者同高，治理职能居顶部），中间参与者（交易主线），底部检票人员（现场职能）——角色的纵向位置即其职能层级。实现手段是隐藏锚点边（仅用于定位，不表达任何关系）：两条角色间隐藏边固定左列"组织者→参与者→检票人员"的上下顺序，一条把平台管理员钉到顶部高度带，三条隐藏链把管理员的 4 个用例按业务顺序钉成其右侧一列；管理员的连线因此全部指向右方，与其余角色"用例在右"的方向一致。

1. **参与者 —— 注册登录 / 查询演出 / 购票 / 候补 / 自助退票**
   - 逻辑关系：参与者的完整闭环。
   - 设计原因：这五件事覆盖了 REQ-001、005、006、008、009，是参与者能做的全部写操作。

2. **注册登录 ..> 实名认证（include）**
   - 逻辑关系：注册后必须实名，不能跳过。
   - 设计原因：实名是购票的前置条件（REQ-001、REQ-006），用 include 表示"每次登录流程都包含"；若用 extend 会误导成可选。

3. **购票 ..> 实名限购校验（include）**
   - 逻辑关系：每次购票都要先校验"同一场次是否已有票"。
   - 设计原因：限购是强制的，不是分支（REQ-006）。

4. **核销票码 ..> 校验签到窗口（include）**
   - 逻辑关系：核销前必须先确认签到窗口已开启。
   - 设计原因：窗口未开启时核销必须被拒绝（REQ-011），这是必经步骤。

5. **候补 ..> 购票（extend）**
   - 逻辑关系：售罄时购票流程多出一个"转候补"的可选分支。
   - 设计原因：候补不是每次购票都会发生，用 extend 而非 include（REQ-008）。

6. **检票人员 —— 只有"核销票码"一个用例**
   - 逻辑关系：检票人员没有任何查询用例。
   - 设计原因：REQ-005 明确"检票人员无查询功能"，图上不画就是设计约束的体现（REQ-024 最小信息）。

7. **平台管理员 —— 审核演出申请 / 开启签到窗口 / 封禁账号 / 查询审计日志**
   - 逻辑关系：管理员只做治理，不参与交易。
   - 设计原因：审核、开窗、封禁、审计四项分别对应 REQ-003、011、017、016，且都是"平台侧"操作。

8. **（写作提示）为什么没有"用户"基类 actor**
   - 这四个角色确实共享"登录"，但画成 actor 泛化后四条线绕行画布外，可读性明显下降。此处选择保留四类独立角色、在类图里表达共享结构。这条取舍建议连同尝试过程写进大模型使用章节。

## 3.4 活动图

图展示购票主流程，三条泳道：参与者、售票模块、候补与退款模块。

1. **判断"票档有余票"**
   - 逻辑关系：提交订单后第一件事是余票判断，有则扣减建单，无则转候补。
   - 设计原因：把校验放在最前，避免"先建单后失败"产生垃圾订单（REQ-006、REQ-020）。

2. **while（未支付且未超时）轮询支付结果**
   - 逻辑关系：订单进入待支付后有 3 分钟窗口，轮询检查支付结果。
   - 设计原因：明确"超时"是循环的出口条件之一，而不是事后补救（REQ-007）。

3. **fork：生成票码 / 写审计日志 并行**
   - 逻辑关系：支付成功后两件事互不依赖，可并行。
   - 设计原因：出票（REQ-007）与留痕（REQ-016）分开，日志失败不应阻塞出票，反之亦然。

4. **支付失败的 else 分支：关闭订单 → 释放名额 → 通知候补首位 → 递补出票**
   - 逻辑关系：超时未支付的名额要回流，并自动补给队列首位。
   - 设计原因：这是 REQ-008 的"自动递补"，也是"名额不丢失"的保证（REQ-020）。

5. **"无余票"分支 → 提交候补并预付 → 加入队尾**
   - 逻辑关系：售罄后不是简单报错，而是给出候补路径。
   - 设计原因：对应 REQ-008 的候补与预付；预付是递补后能立即出票的前提。

6. **（写作提示）活动图与状态图的分工**
   - 活动图回答"一次业务怎么走"，状态图回答"一个对象能变成什么"。两张图都画不是重复，而是分别覆盖流程与数据。

## 3.5 时序图

图展示"退票与自动递补"。对象名与类图的领域对象对应（订单、票档、候补记录、审计日志）；"候补退款服务"是服务类、"站内通知"是消息对象，按第 3.1 节的取舍不在类图中出现，它们分别对应组件图的 M5 与 M8。

1. **为什么不画"购票"**
   - 逻辑关系：购票流程已经在活动图里展开。
   - 设计原因：两张图覆盖不同业务（买票 vs 退票递补），合起来覆盖 REQ-006/007 与 REQ-008/009/021，避免同一流程画两遍。

2. **查询订单状态与开演时间**
   - 逻辑关系：退票前必须确认订单已出票、且距开演多久。
   - 设计原因：阶梯手续费依赖时间差，时间必须取自服务端（REQ-009）。

3. **自调用"计算手续费（40%）"**
   - 逻辑关系：纯计算，不依赖外部对象。
   - 设计原因：把规则计算收在服务内部，金额错误只可能出在一个地方（REQ-021）。

4. **alt：距开演超过 3 天允许退票 / 不足 3 天拒绝**
   - 逻辑关系：可退与不可退是两条互斥路径。
   - 设计原因：对应 REQ-009 的阶梯规则（>7 天 20%、3–7 天 40%、<3 天禁止）。

5. **释放 1 个名额 → 通知 → 取队首 → loop 递补**
   - 逻辑关系：退票释放名额后，按队列顺序逐个递补，直到队列空或名额用完。
   - 设计原因：loop 的条件写"队列非空且有余票"，直接表达 REQ-008 的自动递补与 REQ-020 的不超售。

6. **写入退票与递补审计日志**
   - 逻辑关系：一次退票可能触发多次递补，全部落日志。
   - 设计原因：REQ-016 要求可追溯；流程末尾统一写，避免中途失败留下半条记录。

## 3.6 状态图（加分项）

图展示订单的 9 个状态、9 条允许转换与 5 个终态，逐条对应 REQ-023。呈现上采用从左到右的时间流向：主链 [*]→待支付→已出票→已签到→已核销→[*] 横贯中部；"超时关闭"钉在待支付上方、"活动取消或改期退款"钉在已出票正下方，两条提前退场线沿顶边、底边对称汇入结束节点，"候补退出"也因此成为贴底短弧；取消、缺席从已出票向右扇出。用双色区分进行中状态（蓝灰底）与 5 个终态（米色底，右下角图例说明）。全程无交叉。

1. **两个初始转换：[*] → 待支付、[*] → 候补中**
   - 逻辑关系：正常下单进入待支付；候补单提交并预付后直接进入候补中。
   - 设计原因：REQ-023 列的 9 条允许转换里没有"待支付 → 候补中"，所以用第二个初始转换表达候补入口，保证与需求文档完全一致。

2. **待支付 → 已出票 / 已关闭**
   - 逻辑关系：3 分钟内支付成功出票，超时关闭并回池。
   - 设计原因：一对互斥出口，对应 REQ-007 的超时规则。

3. **候补中 → 已出票 / 已退款**
   - 逻辑关系：递补成功出票；主动退出或截止未递补则退款。
   - 设计原因：候补只有两条正当出口，防止"候补中未递补直接出票"（REQ-008、REQ-023）。

4. **已出票 → 已签到 / 已缺席 / 已取消 / 已退款**
   - 逻辑关系：出票后有四种去向：核销、缺席、退票、活动取消退款。
   - 设计原因：这四条对应 REQ-011、012、009、010，覆盖"票卖出之后"的全部合法变化。

5. **5 个终态 → [*]**
   - 逻辑关系：已核销、已缺席、已取消、已关闭、已退款不可再转换。
   - 设计原因：终态是状态机的边界；正文需明确写出"禁止的转换"（如已取消不得回到已出票），图上不画即为约束。
