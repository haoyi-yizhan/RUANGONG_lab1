# 一、项目与软件概述

## 1. 选择的项目

本实验延续实验一的项目：题目 5——活动票务与报名系统。实验一完成了该系统的需求分析，产出 24 条需求（功能需求 18 条、非功能需求 6 条）与配套的访谈记录、验收标准（仓库 lab1-ai-draft / lab1-final 两个标签）。本实验在此需求基线上完成软件设计与建模，产出模块划分、六张 UML 图与十屏 UI 界面。

## 2. 软件的主要功能

系统面向四类角色：参与者（观众）、组织者、检票人员、平台管理员。主要功能如下：

| 功能域 | 说明 | 主要需求 |
|---|---|---|
| 账号与权限 | 手机号注册登录、实名认证、角色权限、忘记密码自助重置、账号封禁 | REQ-001/017/019 |
| 演出发布与审核 | 组织者提交演出申请（含场次与票档），管理员审核（驳回须给原因，可修改再报，不限次数），按约定时间上线 | REQ-002/003/004 |
| 查询与展示 | 按时间、地点、主讲/明星、主题筛选在售演出，查看场次余票（可购/可候补）与购票退票规则公示 | REQ-005 |
| 购票与支付 | 实名购票（每账号每场次限购 1 张），3 分钟站内模拟支付，出票时后台按票档统一分配座位并生成唯一票码 | REQ-006/007 |
| 候补与退款 | 票档售罄转候补，预付全款排队，递补自动出票，截止未递补全额原路退回；阶梯退票（>7 天收 20%、3–7 天收 40%、不足 3 天不可退） | REQ-008/009/021 |
| 演出变更 | 改期/改址须重新审核，通过后站内通知全部已购票用户，用户可选按原价全额退款 | REQ-010 |
| 检票入场 | 管理员开启签到窗口（演出前约 3 小时），检票员输入票码并核对身份证核销放行；演出结束未检票转缺席 | REQ-011/012 |
| 统计与导出 | 按场次统计上座率、购票总人数、实际到场、候补、退票；组织者导出观众名单（姓名、联系方式、座位号） | REQ-014/015 |
| 全程审计 | 关键操作（审核、支付、退票、核销、封禁、导出等）记录操作者/时间/动作/对象/前后值，不可删改 | REQ-016 |

## 3. 明确不实现的内容

不接入真实支付与短信（站内模拟支付、站内消息）；不做二维码与人脸识别（入场凭证为唯一票码字符串）；不做座位图选座（后台按票档统一分配）；不做公益免费票与票转让（REQ-013 已拒绝）；不做黄牛自动检测（实名限购 + 管理员手动封禁替代）。

## 4. 数据与状态约束

设计与后续实现共同遵守以下约束（详见类图与状态图）：

- 订单状态机共 9 个状态：待支付、候补中、已出票、已签到、已核销、已缺席、已取消、已关闭、已退款；其中 5 个终态不可再转换。
- 可售余票 = 票档总量 − 有效订单数（待支付与已出票），随支付、关闭、退票、递补实时同步；票档售罄自动转候补。
- 退款金额 = 实付金额 − 应扣手续费，原路退回。
- 唯一性约束：手机号、身份证号、票码全平台唯一；同一账号同一场次仅一条有效订单。

### 1. 划分原则

**原则一：按业务生命周期切，不按技术层切。**
活动从"申请 → 审核 → 上线 → 售票 → 检票 → 统计"是一条链，每个环节的责任人不同（组织者、管理员、参与者、检票人员）。按这条链切模块，模块边界与权限边界自然重合，后续做权限控制和用例图都不会打架。

**原则二：一个共享数据只留一个写入口。**
全系统最敏感的数据是「票档余票」。若售票模块和候补退款模块都能改已售数，就必然出现超售（违反 REQ-020）。因此余票的写入口只保留在售票模块，候补退款模块退票后只能"申请释放名额"，由售票模块实际回池。

**原则三：横切关注点收敛到支撑模块。**
审计日志、站内通知、故障回退被几乎所有模块使用。若每个业务模块各写一套，日志格式、通知渠道会各说各话。因此统一收敛到平台支撑模块。

**原则四：职责单一到"只有一个变更理由"。**
统计规则变了只动统计模块；审核流程变了只动活动模块；票务规则变了才动售票模块。

### 2. 模块清单

| 编号 | 模块 | 一句话职责 | 覆盖需求 |
|---|---|---|---|
| M1 | 账号与权限模块 | 注册登录、实名认证、四类角色权限、封禁 | REQ-001、017、019、024 |
| M2 | 活动发布与审核模块 | 活动/场次/票档的提交、审核、上线、改期取消 | REQ-002、003、004、010 |
| M3 | 查询展示模块 | 多条件查询、余票状态、规则公示 | REQ-005 |
| M4 | 售票模块 | 限购校验、下单、模拟支付、出票、余票扣减 | REQ-006、007、020、023 |
| M5 | 候补与退款模块 | 候补队列、自动递补、阶梯退票、退款执行 | REQ-008、009、021 |
| M6 | 检票模块 | 签到窗口、票码核销、缺席判定 | REQ-011、012 |
| M7 | 统计与导出模块 | 场次统计、名单导出 | REQ-014、015 |
| M8 | 平台支撑模块 | 审计日志、站内通知、一致性保障 | REQ-016、022 |

#### M1 账号与权限模块
- **负责**：手机号+密码注册/登录/重置；实名认证（姓名+身份证号，双向唯一）；四类角色的权限判定；管理员封禁与解封。
- **不负责**：不判断"这个用户能不能买这一场"（那是 M4 的限购规则），也不管可见字段过滤（那是各查询模块按角色取数）。
- **对外能力**：登录校验、当前用户身份与角色、实名信息读取、封禁状态检查。
- **依赖**：M8（封禁操作留痕）。

#### M2 活动发布与审核模块
- **负责**：活动与场次、票档的创建与提交；管理员审核（通过/驳回+必填原因，不设次数上限）；按约定时间上线；改期/改址/取消的申请与审核；活动主线状态流转（待审核→上线→在售中→已截止→检票中→已结束/已取消）。
- **不负责**：不卖票、不算余票（M4），不负责通知投递（M8）。
- **对外能力**：可售场次与票档查询、报名截止时间、签到窗口控制。
- **依赖**：M8（改期/取消后的站内通知、审计日志）。

#### M3 查询展示模块
- **负责**：按时间、地点、主演或主讲、主题多条件筛选在售活动；展示各场次余票状态（可购/可候补/已售罄）与购票退票规则；组织者查看自己活动的售票情况与审核进度；管理员按活动编号/订单号/用户 ID 查询。
- **不负责**：不计算结果性数据，余票与统计一律向 M4、M7 取。
- **依赖**：M2（活动数据）、M4（余票实时数）。

#### M4 售票模块
- **负责**：限购校验（每账号每场次限 1 张）；创建订单并进入待支付；3 分钟模拟支付与超时关闭；出票（按票档统一分配座位、生成唯一票码）；**余票扣减与回池的唯一写入口**；订单状态机（9 状态、9 条允许转换）。
- **不负责**：不维护候补队列（M5），不核销（M6）。
- **对外能力**：下单、支付、查余票、关闭订单、释放名额（供 M5 退票调用）。
- **依赖**：M1（实名与限购所需身份）、M8（审计日志）。

#### M5 候补与退款模块
- **负责**：票档售罄后的候补申请与预付；按先来后到维护唯一队列；出现名额时自动递补首位并出票；阶梯退票手续费计算（>7 天 20%、3–7 天 40%、不足 3 天禁止）；退款金额与"实付−手续费"严格一致；候补失败全额退款。
- **不负责**：不直接改票档已售数（必须调 M4 的释放名额接口），不直接改订单状态为已出票（由 M4 出票）。
- **依赖**：M4（释放名额、出票）、M8（退款通知、审计日志）。

#### M6 检票模块
- **负责**：签到窗口开启（演出前约 3 小时）；输入票码+核对身份证号核销；重复核验、已取消、伪造票码、窗口未开四种异常分别提示；演出结束后未检票订单转已缺席。
- **不负责**：不提供任何查询功能（REQ-005 明确检票人员无查询权限）。
- **依赖**：M4（订单与票码）、M2（场次与签到窗口）、M8（审计日志）。

#### M7 统计与导出模块
- **负责**：按场次统计出票数、到场人数、候补人数、退票数、上座率；按活动/场次导出名单（姓名、联系方式、座位号，**不含身份证号**）；导出行为留审计。
- **不负责**：不持有业务数据，只聚合 M4/M5/M6 的记录。
- **依赖**：M4、M5、M6（数据源）、M8（导出审计）。

#### M8 平台支撑模块
- **负责**：审计日志（操作者、时间、动作、对象、状态前后值；不可删改、可按对象查询）；站内通知（改期/取消、候补递补、退款结果）；一致性保障（故障恢复后"要么完成要么回退"，不留半完成订单）。
- **不负责**：不承载业务规则。
- **被依赖**：M1～M7。
- **说明**：站内通知与模拟支付都是**系统内部能力**——通知由 M8 承载；模拟支付是独立的站内模拟组件（REQ-007，本项目不接入真实支付），不属于 M1～M8 的业务模块编号。

### 3. 模块间交互

#### 3.1 主流程的调用链

| 业务流程 | 调用链 |
|---|---|
| 活动上线 | 组织者 → M2 提交 → M2 请求 M8 记审核 → M2 上线 → M8 通知 |
| 购票 | M3 查询 → M4 限购校验 → M4 扣减余票 → M4 创建订单 → 待支付 → 支付成功 → M4 出票 → M8 记日志 |
| 售罄转候补 | M4 返回"售罄" → 调用方转 M5 提交候补（预付）→ M5 入队 |
| 退票递补 | M5 算手续费 → M5 调 M4 释放名额 → M4 回池 → M4 通知 M5 递补 → M5 取队首 → M4 出票 |
| 检票 | M6 校验窗口 → M6 核验票码+身份证 → M4 订单转已签到 → M8 记日志 |
| 统计导出 | M7 聚合 M4/M5/M6 → 生成报表/名单 → M8 记导出审计 |
| 活动取消 | M2 审核通过 → M5 全额退款 → M8 通知全部购票用户 |

#### 3.2 共享数据的归属与同步

| 数据 | 唯一所有者 | 谁可以读 | 谁可以写 |
|---|---|---|---|
| 票档余票（已售数） | M4 | M3、M5、M7 | **仅 M4** |
| 订单与票码 | M4 | M5、M6、M7 | M4（状态转换）；M6 只能触发"已签到" |
| 候补队列 | M5 | M7 | 仅 M5 |
| 审计日志 | M8 | 管理员 | 各模块通过 M8 追加，无人可改 |
| 活动/场次/票档定义 | M2 | M3、M4、M6、M7 | 仅 M2（上线后容量与价格冻结） |

**同步规则**：任一票档可售余票 = 总量 − 有效订单数（待支付 + 已出票）。支付、超时关闭、退票、递补四种事件发生后，都由 M4 在同一个事务里更新余票并写日志（REQ-020、REQ-022）。

#### 3.3 依赖方向

```
M8（无业务依赖，被所有人依赖）
M1 ← M4, M6, M3, M7
M2 ← M3, M4, M6
M4 ← M3, M5, M6, M7
M5 ← M7
M6 ← M7
```

设计上要求**依赖不成环**：M4 不反向依赖 M5。售罄时 M4 只返回"售罄"结果，由购票流程（上层）去调 M5，这样 M4 与 M5 之间保持单向。这是本设计里唯一需要小心处理的耦合点。

#### 4.2 非功能需求（6 条）——横切，不单独成模块

非功能需求没有"行为"，强行做成模块会得到一个空壳。正确做法是给每条指出**落在哪些模块的哪个环节**，并说明设计上靠什么保证。

| 编号 | 需求名称 | 落点 | 设计上如何保证 |
|---|---|---|---|
| REQ-018 | 查询响应性能 | M3、M4 | 查询走只读路径（M3 不写业务数据）；余票由订单推导，不维护冗余计数 |
| REQ-019 | 密码存储安全 | M1 | 只存密码哈希；任何接口不返回密码字段 |
| REQ-020 | 购票数据一致性（不超售、队列有序） | M4（M5 配合） | 余票唯一写入口在 M4；候补记录以排队序号排序 |
| REQ-021 | 退款金额一致性 | M5 | 退款与手续费在同一个服务方法内计算并落库 |
| REQ-022 | 故障回退与可靠性 | M8（横切全部写操作） | 扣名额、建订单、写日志放在同一事务；失败整体回退 |
| REQ-024 | 角色数据可见范围 | M1 + M3/M7 取数 | 角色判定集中在 M1；查询模块按角色裁剪返回字段 |

#### 4.3 按模块反查（检查有没有模块是空的）

| 模块 | 主责需求 | 配合的需求 |

### 3.1 类图

图展示核心领域模型：14 个类（含 2 个 «同一类» 副本）。模块归属用底色区分——蓝 = M1 账号与权限，绿 = M2 活动发布与审核，橙 = M4+M5 交易，紫 = M6+M7 现场与运营，灰 = M8 平台支撑。不画包框而用配色，是为了让布局引擎自由排布、做到连线零交叉；模块与类的完整对应见第二章 4.3 节的反查表。

此外有四处呈现技巧：① 布局按"从上到下读"设计——右上角是账号体系（四个角色泛化箭头向上指向用户，教科书惯例），中轴是业务主链（组织者提交 → 活动 → 场次 → 票档 → 订单 → 审计日志，垂直向下），左侧一列是与主链各环节一一对应的记录（检票记录对应场次核销、候补记录对应票档排队），退款作为订单的关联放在主链右侧收尾，读图顺序即业务顺序；② 参与者与组织者各有一个带构造型 «同一类» 的副本，就近画在订单与活动旁边——UML 允许同一元素在图中出现多次，副本只承担业务关联（购买、提交），继承关系由右侧的角色原块表达，两条线因此从横贯全图变成局部短线；③ 审计日志与业务对象之间只画出"订单 → 审计日志"一条依赖线作为代表，活动、检票等对象的写入不再重复，图旁注释已说明；④ 布局方向逐条手工指定（-up-/-down-/-left-/-right-），保证连线零交叉。

**取舍原则**：能说明"业务对象是什么、谁归谁"的保留；派生数据、横切记录、架构层对象一律不进类图。被移出的对象及去向见本节末尾。

1. **参与者 / 组织者 / 检票人员 / 平台管理员 —— 泛化自 用户**
   - 逻辑关系：四类角色共享账号、实名与状态，只在"能做什么"上不同。
   - 设计原因：登录、实名、状态若各写一遍要重复四份；泛化后权限判定集中在一处（REQ-001、REQ-024）。

2. **用户（含角色、实名、封禁状态字段）**
   - 逻辑关系：角色用枚举取值表达（参与者/组织者/检票人员/管理员），与四个角色子类互为呼应；姓名、身份证号承载实名。
   - 设计原因：实名与封禁都是"账号的属性"而非独立业务对象；封禁的多次操作记录由审计日志承担（REQ-001、REQ-017）。

3. **组织者 1 —— \* 活动**
   - 逻辑关系：活动必须属于一个组织者，一个组织者可办多个活动。
   - 设计原因：审核驳回后的修改、下线后的追责都依赖这条归属（REQ-002、REQ-003）。

4. **活动 1 ◆—— 1..\* 场次（组合）**
   - 逻辑关系：场次脱离活动没有意义，活动取消后场次一并失效。
   - 设计原因：生命周期一致；若用聚合，就要额外处理"活动已删、场次还在"的脏数据（REQ-004）。

5. **场次 1 ◆—— 1..\* 票档（组合）**
   - 逻辑关系：票档是场次内的价格分区，场次删除后票档不存在。
   - 设计原因：座位分配、余票扣减、统计都以票档为最小单位（REQ-004、REQ-015）。

6. **活动 1 —— \* 审核记录**
   - 逻辑关系：一个活动可能经历多轮审核（驳回→修改→再申请，次数不限）。
   - 设计原因：只保留最新结论会丢失历史，而驳回原因是组织者修改的依据（REQ-003）。

7. **参与者 1 —— \* 订单**
   - 逻辑关系：一个人可买多个不同场次的票；同一场次限购 1 张。
   - 设计原因：限购是业务规则（由售票过程校验），不是数据结构限制，所以关系用一对多（REQ-006）。

8. **票档 1 —— \* 订单**
   - 逻辑关系：订单从某个票档售出；可售余票 = 总量 − 有效订单数。
   - 设计原因：余票不单独存字段，而是由订单推导，避免"余票与实际订单不一致"（REQ-020）。

9. **订单 1 —— 0..1 退款**
   - 逻辑关系：只有退票、活动取消、候补失败等情况才有退款，一单最多一笔。
   - 设计原因：用 0..1 表达"不是每单都退"；退款金额与手续费必须可核对（REQ-009、REQ-021）。

10. **订单.状态 字段**
    - 逻辑关系：订单状态有 9 种取值，类图中以字段表示，完整的状态机单独画在状态图里。
    - 设计原因：状态机是独立的一张图（REQ-023），类图里再画一个 9 行的枚举框只会增加高度，不增加信息。

11. **票档 1 —— \* 候补记录**
    - 逻辑关系：同一票档只有一条候补队列，记录按排队序号排序。
    - 设计原因：队列顺序是硬要求，序号必须显式存储（REQ-008、REQ-020）。

12. **候补记录 ..> 订单（依赖）**
    - 逻辑关系：递补成功时才生成订单。
    - 设计原因：候补记录先存在、订单后产生，两者不同时创建，用依赖而非组合（REQ-008）。

13. **场次 1 —— \* 检票记录；订单 1 —— 0..1 检票记录**
    - 逻辑关系：一次核销关联"哪个场次、哪张票"；检票员以属性记录。
    - 设计原因：按场次查到场人数、按票识别重复核验；订单端 0..1 保证重复核验能被识别（REQ-011、REQ-012）。

14. **审计日志独立存在**
    - 逻辑关系：只记对象类型 + 对象ID + 状态前后值，不与业务类建立关联。
    - 设计原因：给每个类都连一条线会变成蜘蛛网；用 ID 引用实现同样的可追溯性（REQ-016）。

### 3.2 组件图

图展示 8 个业务模块、1 个站内模拟支付组件、2 个对外接口和若干依赖关系，四类角色用户位于系统框外顶部。布局按调用方向分四层：顶部是四类角色用户；其下一行是对外接口与发起调用的模块（查询展示、账号与权限、统计与导出、检票、候补与退款）；再下是被依赖的售票(M4)与活动发布与审核(M2)——M4 被 4 个模块依赖，是全局枢纽，故置于图的中心；底部是平台支撑(M8)与模拟支付。接口符号只留给被多方复用的能力：登录面向全部四类角色、下单被候补与退款(M5)递补复用，二者画在系统框内、紧贴所属模块；核销仅检票人员一人使用，由角色直达检票(M6)，不设接口符号，角色出发的三条线因此呈扇形展开、互不交叉。模拟支付是系统内的模拟支付网关组件——REQ-007 确认本项目不接入真实支付，独立成组件以便日后替换真实支付，故不标注为外部系统。依赖方向自上而下，全程无交叉；实现上用少量隐藏锚点边固定行列顺序（仅定位、不表达关系）。每个模块框内以小字标注该模块的代表性职责，与第二章模块划分对应。

1. **账号与权限(M1) — 登录接口**
   - 逻辑关系：所有角色登录都经过 M1，M1 对外暴露"登录"。
   - 设计原因：把鉴权收敛到一个组件，其他模块不再各自校验密码（REQ-001、REQ-019）。

2. **售票(M4) — 下单接口；候补与退款(M5) 使用同一下单接口**
   - 逻辑关系：下单是 M4 提供的唯一写入口，M5 递补出票时复用。
   - 设计原因：同一个入口才能保证限购与余票校验不被绕过（REQ-006、REQ-020）。

3. **检票人员 → 检票(M6)：核销票码**
   - 逻辑关系：检票人员是核销的唯一使用者，直达模块。
   - 设计原因：核销涉及座位、票码、签到窗口，收在 M6 内独占校验逻辑（REQ-011）；接口符号只留给被复用的能力（登录、下单），核销单一入口，直连更直观。

4. **查询展示(M3) ..> 售票(M4)：查询余票；查询展示(M3) ..> 活动发布与审核(M2)：查询活动**
   - 逻辑关系：M3 只读，不写任何业务数据。
   - 设计原因：读写分离，查询压力不落到写入口上（REQ-005、REQ-018）。

5. **候补与退款(M5) ..> 售票(M4)：释放名额**
   - 逻辑关系：M5 退票后请求 M4 回池，自己不直接改已售数。
   - 设计原因：这是"余票唯一写入口"的落地方式，也是避免超售的关键（REQ-020）。

6. **售票(M4) ..> 模拟支付：发起模拟支付**
   - 逻辑关系：M4 调用站内模拟支付完成收款，支付结果回写订单。
   - 设计原因：REQ-007 确认不接入真实支付、只做站内模拟；独立成组件并只依赖其接口，模拟收单与原路退回（REQ-021）都在该组件内，日后替换真实支付只改这一处。

7. **售票(M4) ..> 平台支撑(M8)：写审计日志；活动发布与审核(M2) ..> 平台支撑(M8)：发送站内通知**
   - 逻辑关系：所有模块的关键操作都写入 M8，图中只画两条代表线。
   - 设计原因：横切能力集中，避免每个模块各写一套日志与通知（REQ-016、REQ-010）。

### 3.3 用例图

图展示 4 类角色、16 个用例、3 个 include 与 1 个 extend。未画系统边界框：图题已表明系统范围，且用例按角色分组排列，边界自明。布局分四层：左上组织者、右上平台管理员（两者同高，治理职能居顶部），中间参与者（交易主线），底部检票人员（现场职能）——角色的纵向位置即其职能层级。实现手段是隐藏锚点边（仅用于定位，不表达任何关系）：两条角色间隐藏边固定左列"组织者→参与者→检票人员"的上下顺序，一条把平台管理员钉到顶部高度带，三条隐藏链把管理员的 4 个用例按业务顺序钉成其右侧一列；管理员的连线因此全部指向右方，与其余角色"用例在右"的方向一致。

1. **参与者 —— 注册登录 / 查询演出 / 购票 / 候补 / 自助退票**
   - 逻辑关系：参与者的完整闭环。
   - 设计原因：这五件事覆盖了 REQ-001、005、006、008、009，是参与者能做的全部写操作。

2. **注册登录 ..> 实名认证（include）**
   - 逻辑关系：注册后必须实名，不能跳过。
   - 设计原因：实名是购票的前置条件（REQ-001、REQ-006），用 include 表示"每次登录流程都包含"；若用 extend 会误导成可选。

3. **购票 ..> 实名限购校验（include）**
   - 逻辑关系：每次购票都要先校验"同一场次是否已有票"。
   - 设计原因：限购是强制的，不是分支（REQ-006）。

4. **核销票码 ..> 校验签到窗口（include）**
   - 逻辑关系：核销前必须先确认签到窗口已开启。
   - 设计原因：窗口未开启时核销必须被拒绝（REQ-011），这是必经步骤。

5. **候补 ..> 购票（extend）**
   - 逻辑关系：售罄时购票流程多出一个"转候补"的可选分支。
   - 设计原因：候补不是每次购票都会发生，用 extend 而非 include（REQ-008）。

6. **检票人员 —— 只有"核销票码"一个用例**
   - 逻辑关系：检票人员没有任何查询用例。
   - 设计原因：REQ-005 明确"检票人员无查询功能"，图上不画就是设计约束的体现（REQ-024 最小信息）。

7. **平台管理员 —— 审核演出申请 / 开启签到窗口 / 封禁账号 / 查询审计日志**
   - 逻辑关系：管理员只做治理，不参与交易。
   - 设计原因：审核、开窗、封禁、审计四项分别对应 REQ-003、011、017、016，且都是"平台侧"操作。

8. **（写作提示）为什么没有"用户"基类 actor**
   - 这四个角色确实共享"登录"，但画成 actor 泛化后四条线绕行画布外，可读性明显下降。此处选择保留四类独立角色、在类图里表达共享结构。这条取舍建议连同尝试过程写进大模型使用章节。

### 3.4 活动图

图展示购票主流程，三条泳道：参与者、售票模块、候补与退款模块。

1. **判断"票档有余票"**
   - 逻辑关系：提交订单后第一件事是余票判断，有则扣减建单，无则转候补。
   - 设计原因：把校验放在最前，避免"先建单后失败"产生垃圾订单（REQ-006、REQ-020）。

2. **while（未支付且未超时）轮询支付结果**
   - 逻辑关系：订单进入待支付后有 3 分钟窗口，轮询检查支付结果。
   - 设计原因：明确"超时"是循环的出口条件之一，而不是事后补救（REQ-007）。

3. **fork：生成票码 / 写审计日志 并行**
   - 逻辑关系：支付成功后两件事互不依赖，可并行。
   - 设计原因：出票（REQ-007）与留痕（REQ-016）分开，日志失败不应阻塞出票，反之亦然。

4. **支付失败的 else 分支：关闭订单 → 释放名额 → 通知候补首位 → 递补出票**
   - 逻辑关系：超时未支付的名额要回流，并自动补给队列首位。
   - 设计原因：这是 REQ-008 的"自动递补"，也是"名额不丢失"的保证（REQ-020）。

5. **"无余票"分支 → 提交候补并预付 → 加入队尾**
   - 逻辑关系：售罄后不是简单报错，而是给出候补路径。
   - 设计原因：对应 REQ-008 的候补与预付；预付是递补后能立即出票的前提。

6. **（写作提示）活动图与状态图的分工**
   - 活动图回答"一次业务怎么走"，状态图回答"一个对象能变成什么"。两张图都画不是重复，而是分别覆盖流程与数据。

### 3.5 时序图

图展示"退票与自动递补"。对象名与类图的领域对象对应（订单、票档、候补记录、审计日志）；"候补退款服务"是服务类、"站内通知"是消息对象，按第 3.1 节的取舍不在类图中出现，它们分别对应组件图的 M5 与 M8。

1. **为什么不画"购票"**
   - 逻辑关系：购票流程已经在活动图里展开。
   - 设计原因：两张图覆盖不同业务（买票 vs 退票递补），合起来覆盖 REQ-006/007 与 REQ-008/009/021，避免同一流程画两遍。

2. **查询订单状态与开演时间**
   - 逻辑关系：退票前必须确认订单已出票、且距开演多久。
   - 设计原因：阶梯手续费依赖时间差，时间必须取自服务端（REQ-009）。

3. **自调用"计算手续费（40%）"**
   - 逻辑关系：纯计算，不依赖外部对象。
   - 设计原因：把规则计算收在服务内部，金额错误只可能出在一个地方（REQ-021）。

4. **alt：距开演超过 3 天允许退票 / 不足 3 天拒绝**
   - 逻辑关系：可退与不可退是两条互斥路径。
   - 设计原因：对应 REQ-009 的阶梯规则（>7 天 20%、3–7 天 40%、<3 天禁止）。

5. **释放 1 个名额 → 通知 → 取队首 → loop 递补**
   - 逻辑关系：退票释放名额后，按队列顺序逐个递补，直到队列空或名额用完。
   - 设计原因：loop 的条件写"队列非空且有余票"，直接表达 REQ-008 的自动递补与 REQ-020 的不超售。

6. **写入退票与递补审计日志**
   - 逻辑关系：一次退票可能触发多次递补，全部落日志。
   - 设计原因：REQ-016 要求可追溯；流程末尾统一写，避免中途失败留下半条记录。

### 3.6 状态图（加分项）

图展示订单的 9 个状态、9 条允许转换与 5 个终态，逐条对应 REQ-023。呈现上采用从左到右的时间流向：主链 [*]→待支付→已出票→已签到→已核销→[*] 横贯中部；"超时关闭"钉在待支付上方、"活动取消或改期退款"钉在已出票正下方，两条提前退场线沿顶边、底边对称汇入结束节点，"候补退出"也因此成为贴底短弧；取消、缺席从已出票向右扇出。用双色区分进行中状态（蓝灰底）与 5 个终态（米色底，右下角图例说明）。全程无交叉。

1. **两个初始转换：[*] → 待支付、[*] → 候补中**
   - 逻辑关系：正常下单进入待支付；候补单提交并预付后直接进入候补中。
   - 设计原因：REQ-023 列的 9 条允许转换里没有"待支付 → 候补中"，所以用第二个初始转换表达候补入口，保证与需求文档完全一致。

2. **待支付 → 已出票 / 已关闭**
   - 逻辑关系：3 分钟内支付成功出票，超时关闭并回池。
   - 设计原因：一对互斥出口，对应 REQ-007 的超时规则。

3. **候补中 → 已出票 / 已退款**
   - 逻辑关系：递补成功出票；主动退出或截止未递补则退款。
   - 设计原因：候补只有两条正当出口，防止"候补中未递补直接出票"（REQ-008、REQ-023）。

4. **已出票 → 已签到 / 已缺席 / 已取消 / 已退款**
   - 逻辑关系：出票后有四种去向：核销、缺席、退票、活动取消退款。
   - 设计原因：这四条对应 REQ-011、012、009、010，覆盖"票卖出之后"的全部合法变化。

5. **5 个终态 → [*]**
   - 逻辑关系：已核销、已缺席、已取消、已关闭、已退款不可再转换。
   - 设计原因：终态是状态机的边界；正文需明确写出"禁止的转换"（如已取消不得回到已出票），图上不画即为约束。

# 四、UI 界面设计

## 1. 设计规范与终端形态

十屏界面遵循统一视觉规范：边框 #7C8AA0、页面底色 #EEF2F7、卡片 #FFFFFF、主文字 #334155、辅助文字 #6B7A8C/#8A97A6，字体微软雅黑；控件规格全组一致（主按钮高 44px、徽标高 22px、卡片圆角 8–12px）。

终端形态按角色使用场景分配：参与者购票是随身场景，界面 1–6 采用网页门户形态（居中卡片、底部页签）；组织者、管理员、检票员的操作是工作台场景，界面 7–10 采用控制台形态（宽表单、表格与统计卡）。界面源文件为 .drawio 格式，经 draw.io 官方导出服务渲染为 PNG。

## 2. 界面清单与功能描述

### 界面 1　登录 / 注册（未登录态）

手机号 + 密码登录，登录/注册页签切换，忘记密码自助重置入口；底部为四角色权限说明卡。检票人员与管理员账号由系统预置，不开放注册。（REQ-001）

### 界面 2　实名认证（已登录未实名）

登录后引导完成实名认证：真实姓名 + 身份证号；同一身份证仅允许绑定一个账号，认证通过前不可购票，认证信息加密存储、仅用于购票与入场核验。（REQ-001、REQ-019、REQ-024）

### 界面 3　演出列表

在售演出卡片流：搜索框，时间/地点/主讲明星/主题四个筛选与"仅看有余票"快捷筛选；卡片展示类型、主演、场次时间地点、票档价格区间与余票状态（有余票 / 可购票 / 售罄转候补）。（REQ-005）

### 界面 4　演出详情与购票

演出横幅与简介、演出须知；右侧为购票/退票规则公示（限购 1 张、阶梯退票）与票档选择（看台/内场/VIP，含余量与价格），选中票档后合计金额随之一致，提交订单进入支付。（REQ-005/006）

### 界面 5　支付与出票

订单摘要（场次/票档/实名观演人/应付金额），3 分钟倒计时条（超时自动关闭、名额回池），站内模拟支付（重复提交仅第一次生效）；支付成功后展示按票档统一分配的座位号与唯一票码。（REQ-007）

### 界面 6　我的订单

订单列表按状态筛选：候补中（预付全款、队列位次、报名截止、可退出候补）、已出票（座位/票码、距开演天数与退票手续费试算、可申请退票）、已退款（原路退回到账）。（REQ-008/009/021）

### 界面 7　组织者-演出管理

新建演出申请表单（名称/主演主讲/类型/报名截止）与场次管理（场次 1 的时间地点 + 票档名称/价格/票数表，可添加票档与场次，上线后容量与票价不可修改）；我的活动列表（草稿/在售/已结束）；审核进度卡。（REQ-002/004/016）

### 界面 8　管理员-审核

待审核申请卡（申请人、场次票档明细、驳回原因必填，通过即按约定时间上线）；改期申请卡（通过并通知全部已购票用户，可按原价全额退款）；账号封禁卡（封禁/解封）；今日待办与最近处理记录。（REQ-003/010/017）

### 界面 9　检票工作台

签到窗口状态条（管理员开启后显示已开启），票码输入 + 身份证后 4 位核对，核销放行；其他情形提示（重复核验 / 伪造或已取消票码 / 窗口未开启）；当日核销记录。（REQ-011）

### 界面 10　统计与导出

六项统计（上座率/购票总人数/实际到场/候补/退票/缺席）与统计口径说明；导出观众名单（姓名、联系方式、座位号，不含身份证号；仅本场次、仅自己的活动，导出记入审计日志）。（REQ-012/014/015/016）

## 3. 界面间数据自洽

演示数据在各屏间交叉一致：界面 4 选中"看台 ¥80"→ 界面 5 应付 ¥80.00、座位"看台 5 排 3 座"→ 界面 9 检票记录同票码；界面 3 的余票状态与界面 7 的票档存量一致；界面 7 的"2 个场次 / 4 个票档"与界面 8 审核卡的申请摘要一致。

# 五、AI 辅助使用记录

本章按"使用场景 → 生成结果 → 优缺点分析 → 修改优化后的结果"四段式记录本实验中每一次有代表性的 AI 使用。使用工具为 ZCode（agent 形态的大模型助手，具备文件读写、多模态图像理解与命令执行能力）；绘图工具为 PlantUML（UML 六图）与 draw.io（UI 十屏，源文件为 .drawio，经 draw.io 官方导出服务渲染 PNG）。

## 5.1 模块划分初稿

- **使用场景**：将实验一定稿的 24 条需求与题目基本要求交给 AI，要求产出模块划分、模块间依赖关系与逐条需求对齐表。
- **生成结果**：8 个模块（M1 账号与权限、M2 活动发布与审核、M3 查询展示、M4 售票、M5 候补与退款、M6 检票、M7 统计与导出、M8 平台支撑）及需求对齐表，即第二章的初稿。
- **优缺点分析**：优点是覆盖完整、速度快，逐条需求对齐表可直接作为后续追踪基线；缺点是模块边界按工程直觉划分，个别职责归属需要人判断——例如检票与售票都涉及订单数据，依赖方向的正确性必须由人对照需求裁决。
- **修改优化后的结果**：逐条核对 24 条需求，修正职责描述与依赖方向，并明确"余票只有一个写入口（M4）"的关键约束，形成第二章定稿。

## 5.2 UML 图生成与迭代（共 6 张）

- **使用场景**：类图、组件图、用例图、活动图、时序图、状态图六张图的 PlantUML 初稿生成，以及此后的布局迭代。
- **生成结果**：六张图的 PlantUML 源码与 PNG；类图达到 14 个类、零连线交叉，状态图采用从左向右的主链布局。
- **优缺点分析**：优点是语法零错误、迭代快——把看到的问题用文字描述给 AI 即可重渲，不需要手工拖拽；缺点是布局引擎的可控性有限：连线交叉、元素重叠需要多轮"人工目检 → 描述问题 → AI 调整"循环才能收敛，且部分方向提示在 left to right 模式下会旋转 90°，一度造成整版返工。
- **修改优化后的结果**：类图经十余轮迭代消除全部交叉；组件图改为按调用方向分层；用例图删除系统边界框后重排；状态图改横版主链布局。迭代过程中 AI 也出现过理解偏差（如把"外部系统"误标到不该标的位置、方向提示不生效），均通过人工指出后修正。

## 5.3 UI 界面生成与渲染（draw.io 源文件）

- **使用场景**：十屏界面的 draw.io 源文件（XML）初稿生成、经 draw.io 官方导出服务渲染 PNG，以及此后按人工意见的逐屏修改。
- **生成结果**：十屏 .drawio 源文件与渲染 PNG；视觉规范全组统一，十屏数据交叉自洽。
- **优缺点分析**：优点是十屏风格绝对统一、修改可精确到坐标、出图即交付格式；缺点是 draw.io 的 XML 为绝对坐标布局，AI 生成的文字与控件容易差几像素互相压线——先后出现标签贴框、长句出框、元素挂错节点不显示等问题；另有一次把"站内模拟支付"错误画成系统外的"外部系统"，混淆了项目边界。
- **修改优化后的结果**：以人工目检与多模态视觉复查发现全部问题并逐屏修正；把"统计口径""已按隐私要求移除"等需求文档语言从界面上清除；按登录态把界面 1 拆分为"登录注册"与"实名认证"两屏。

## 5.4 报告撰写辅助

- **使用场景**：本报告各章节的素材整合与初稿起草。
- **生成结果**：报告草稿——第 2、3 章由既有文档改编，第 4 章（UI）与本章由工作记录整理。
- **优缺点分析**：优点是素材定位与整合速度快、格式统一；缺点是 AI 对"哪些内容属于报告、哪些属于工作笔记"的边界把握需要人复核。
- **修改优化后的结果**：全部章节经本人审阅修改后定稿。【待本人审阅确认】

## 5.5 优缺点总结

- **高效之处**：结构化产出（表、图、界面稿、对照表）的速度优势极大；多模态目检让"AI 画 → 人挑刺 → AI 改"的循环快速收敛；跨屏数据一致性这类可机械验证的问题，AI 可以自查修正。
- **局限**：①对"正确"的判断依赖可检验的标准——需求编号、数据自洽这类能 grep、能比对的它可以自查，而取舍与优先级必须人来定；②长文档的坐标级细节（UI 布局、图形布局）容易压线与出框，需要视觉复查兜底；③会把工作语言（口径、范围、甲方确认）不自觉地带进面向用户的界面，需要人站在"用户看到什么"的立场把关；④生成脚本的一次重跑曾覆盖过人工手改的源文件，文件级协作需要约定修改方式。

## 5.6 两点思考

**大模型如何辅助软件设计**：本实验中它承担的是"把需求翻译成结构化设计产物"的角色——模块划分、UML、界面稿、需求对照表。它的产出质量高度依赖输入的规范程度：实验一留下的结构化需求（编号、验收标准、来源）直接决定了模块划分与 UI 对照的质量；而设计的对错仍由人对照需求裁决。合理的分工是：AI 负责产出候选与机械一致性检查，人负责需求解释、取舍与验收。

**能否设计一套只做检查校对的工作流**：本实验已经部分实现——"AI 产出初稿 → 确定性检查（需求对照表核对、编号 grep、跨屏数据比对）→ 人工目检（多模态视觉）→ 人工终检（draw.io 手改导出）"。在这条流水线上，人的角色从"画图"退到"审图"，每轮修改只需提出意见。它的适用边界也很清楚：凡是能写成检查规则的问题（连线交叉、文字遮挡、编号引用、命名一致、跨屏数据一致）都可以自动化或由 AI 自查；而"这个设计是否合理""这个状态是否应该存在""这个功能要不要做"仍然需要人来判断——本实验中至少有三个问题（模拟支付被画成外部系统、界面 1 的状态矛盾、审核卡缺少场次明细）是规则查不出来、靠人看出来的。
